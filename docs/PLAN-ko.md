# PLAN-ko.md: Rival Everything 기준 개발 계획

## 1. 문서 목적

이 문서는 `Rival Everything`의 기준 기획서다. 기존 문서들의 방향을 무작정 합치지 않고, 현재 구현 상태와 실제 개발 가능한 MVP, Unity 전환, 장기 비전을 분리한다.

현재 프로젝트의 핵심은 거대한 오픈월드나 실시간 전투가 아니라, 다음 루프를 작고 선명하게 검증하는 것이다.

`정체성 선택 -> 딜레마 선택 -> 세계 변화 -> 대칭자의 반대 흔적 -> 통합/회고`

이 루프가 재미있고 이해 가능하다는 것이 확인되기 전에는 Unity 오픈월드, 무한 AI 서사 생성, 복잡한 관계 시뮬레이션, 대형 직업 네트워크를 MVP 범위에 넣지 않는다.

## 2. 핵심 결론

### 유지할 것

- 플레이어의 정체성 선택
- 플레이어와 반대 성향으로 생성되는 대칭자
- 정답이 없는 철학적 딜레마
- 선택에 따라 변하는 세계 상태
- 대칭자의 반대 선택을 지우지 않고 통합하거나 마주하는 엔딩

### 버릴 것

MVP 단계에서는 다음을 만들지 않는다.

- 대형 3D 오픈월드
- 완전한 실시간 전투 RPG
- 장비 파밍과 스킬트리 중심 성장
- 무한 AI 서사 생성
- 복잡한 관계 시뮬레이션
- 대규모 직업 네트워크

### 줄일 것

- 지역 수
- NPC 수
- 직업 수
- 선택지 수
- 텍스트량
- UI 메뉴 수
- AI 생성 범위

### 먼저 만들 것

15분 안에 끝까지 플레이할 수 있는 작은 철학 RPG 버티컬 슬라이스를 만든다. 이 버전은 플레이어가 대칭자의 의미를 이해하고, 자신의 선택이 세계와 반대 가능성을 어떻게 만드는지 체감하는 데 집중한다.

### 위험한 가정

가장 위험한 가정은 "AI가 좋은 철학 딜레마를 저렴하고 안전하게 무한히 생성한다"는 것이다. MVP에서는 이 가정을 사용하지 않는다. 먼저 수작업 딜레마와 규칙 기반 반응으로 핵심 재미를 검증한다.

## 3. 현재 상태

현재 프로젝트는 정적 웹 프로토타입이다.

- `index.html`
- `styles.css`
- `src/app.js`
- `src/game-core.js`
- `tests/core.test.js`

현재 구현된 핵심 루프는 다음과 같다.

1. 플레이어가 3개의 윤리 축을 선택한다.
2. 선택값을 바탕으로 플레이어 정체성이 생성된다.
3. 플레이어와 반대 성향의 대칭자가 생성된다.
4. 작은 섬의 3개 딜레마를 해결한다.
5. 선택에 따라 세계 지표가 변한다.
6. 각 딜레마 이후 대칭자가 다른 장소에 반대 선택의 흔적을 남긴다.
7. 모든 딜레마를 해결하면 대칭자의 흔적 하나를 통합해 엔딩을 본다.

현재 검증된 도메인 모델은 다음과 같다.

- `IdentityProfile`: 플레이어와 대칭자의 윤리 축 프로필
- `Dilemma`: 장소, 축, 선택지, 결과, 세계 변화량
- `RivalMove`: 대칭자가 남기는 반대 선택의 흔적
- `WorldResponse`: 세계 지표와 세계 판정

현재 버전의 한계는 다음과 같다.

- 콘텐츠가 3개 딜레마로 작다.
- 관계와 직업은 아직 구현되어 있지 않다.
- 선택 결과가 장기적으로 누적되는 구조는 제한적이다.
- 모바일 UX, 저장/로드, 접근성은 아직 MVP 수준으로 정리되지 않았다.
- Unity 개발은 아직 시작된 상태가 아니라 장기 전환 목표다.

## 4. 게임의 핵심 정체성

이 게임의 핵심 재미는 "강해져서 적을 이기는 것"이 아니다. 핵심 재미는 "내가 선택한 가치와 내가 선택하지 않은 가능성이 세계를 어떻게 다르게 바꾸는지 보는 것"이다.

대칭자는 단순한 악역이나 최종 보스가 아니다. 대칭자는 플레이어가 선택하지 않은 삶의 가능성이다. 플레이어가 자비를 택하면 대칭자는 효율의 질서를 실현하고, 플레이어가 자유를 택하면 대칭자는 안전한 통제를 확장한다.

철학적 딜레마는 정답 맞히기 문제가 아니어야 한다. 좋은 딜레마는 어떤 선택을 해도 손실, 책임, 오해, 후회, 뜻밖의 선한 결과를 남긴다. 플레이어는 "무엇이 옳은가"보다 "내가 선택한 가치가 어떤 세계를 만드는가"를 보게 된다.

직업, 관계, 오픈월드는 장기 비전에서는 중요하다. 그러나 MVP에서는 독립 시스템이 아니라 핵심 루프를 돕는 장치로만 다룬다.

- 직업은 어떤 종류의 딜레마를 더 자주 마주하는지 정한다.
- 관계는 선택의 기억과 NPC 반응을 보여준다.
- 오픈월드는 넓은 이동 공간이 아니라 선택의 흔적이 남는 장소다.

## 5. 3개월 MVP 범위

### MVP 목표

3개월 MVP의 목표는 출시 가능한 완성형 모바일 RPG가 아니다. 목표는 작은 범위에서 핵심 재미를 검증하는 것이다.

검증할 질문은 다음과 같다.

- 플레이어가 대칭자를 "나와 반대되는 적"이 아니라 "내가 선택하지 않은 가능성"으로 이해하는가?
- 선택 결과가 충분히 불편하고 기억에 남는가?
- 세계 지표와 대칭자의 흔적이 플레이어의 선택을 다시 생각하게 만드는가?
- 5~15분 세션 안에서 피로하지 않게 끝까지 플레이되는가?
- 플레이어가 다른 정체성으로 다시 플레이하고 싶은가?

### 포함할 기능

- 정체성 선택 3축
- 대칭자 자동 생성
- 작은 지역 1개
- 딜레마 5개
- NPC 3~5명
- 세계 지표 3~4개
- 대칭자 흔적 3~5개
- 통합/회고 엔딩 1~2개
- 간단한 저장/재개
- 모바일 기준 UI 흐름

### 제외할 기능

- 대형 오픈월드
- 실시간 전투
- 장비 파밍
- 스킬트리
- 복잡한 인벤토리
- 무한 AI 생성
- 서버 기반 장기 메모리
- 다중 지역 정치/경제 시뮬레이션
- 정식 라이브 운영

### 콘텐츠 범위

MVP 콘텐츠는 "작은 섬 또는 작은 마을 하나"로 제한한다. 지역은 넓지 않아도 된다. 대신 플레이어와 대칭자의 선택 흔적이 다시 보이도록 만든다.

권장 구성은 다음과 같다.

- 시작 지점 1개
- 딜레마 장소 5개
- 대칭자의 흔적이 나타나는 장소 3~5개
- 엔딩 또는 회고 장소 1개

### 성공 기준

소규모 플레이테스트에서 다음 기준을 확인한다.

- 플레이어 70% 이상이 대칭자의 의미를 설명할 수 있다.
- 플레이어 70% 이상이 최소 1개의 선택 결과를 기억한다.
- 평균 플레이 시간이 5~15분 안에 들어온다.
- 텍스트가 길거나 피곤하다는 반응이 과반을 넘지 않는다.
- 다시 다른 선택을 해보고 싶다는 반응이 나온다.

## 6. MVP 게임 루프

### 1. 정체성 선택

플레이어는 3개의 윤리 축에서 자신의 기본 성향을 선택한다. 각 축은 단순한 선악이 아니라 서로 다른 가치의 충돌이어야 한다.

예시:

- 자비 vs 효율
- 자유 vs 질서
- 신뢰 vs 통제

### 2. 대칭자 생성

대칭자는 플레이어의 선택을 반전해 생성된다. 그러나 대칭자는 항상 틀린 존재가 아니다. 대칭자의 선택은 플레이어가 버린 가치가 세계를 구하거나 망칠 수 있음을 보여준다.

### 3. 딜레마 선택

각 딜레마는 하나의 장소, 관련 NPC, 철학 축, 선택지, 결과, 세계 변화량을 가진다. 선택지는 2개로 시작한다. MVP에서는 선택지를 늘리는 것보다 결과의 질을 높인다.

### 4. 세계 상태 변화

플레이어의 선택은 세계 지표를 바꾼다. 지표는 단순 점수가 아니라 세계의 분위기와 NPC 반응을 바꾸는 기준이 되어야 한다.

예시:

- 온기
- 질서
- 숨결
- 균열

### 5. 대칭자의 반대 흔적

플레이어가 한 장소에서 선택하는 동안, 대칭자는 다른 장소에서 반대 성향의 선택을 실현한다. 이 흔적은 플레이어가 나중에 방문해서 확인할 수 있어야 한다.

중요한 점은 대칭자의 흔적이 단순 방해가 아니라는 것이다. 때로는 대칭자의 선택이 실제로 누군가를 살리거나, 플레이어 선택의 약점을 드러내야 한다.

### 6. 통합/회고 엔딩

MVP의 엔딩은 승패 판정이 아니다. 플레이어는 대칭자의 흔적 중 하나를 지우지 않고 통합하거나, 거절하거나, 보류한다. 엔딩은 세계가 하나의 정답을 승인하는 것이 아니라 플레이어의 정체성이 반대의 진실을 견딜 수 있는지 묻는다.

## 7. 데이터 모델

MVP 데이터 모델은 Unity 전환을 염두에 두고 순수 데이터 중심으로 설계한다. 웹 프로토타입에서는 JavaScript 객체로 유지하되, Unity 전환 시 JSON, C# plain model, ScriptableObject로 옮길 수 있어야 한다.

### `IdentityProfile`

플레이어와 대칭자의 정체성을 표현한다.

필드 예시:

- `id`
- `axisSelections`
- `labels`
- `title`
- `history`
- `oppositeRuleVersion`

### `Dilemma`

수작업으로 작성한 딜레마 정의다.

필드 예시:

- `id`
- `locationId`
- `axis`
- `prompt`
- `options`
- `relatedNpcIds`
- `worldDelta`
- `resultText`
- `revisitText`

### `RivalMove`

대칭자가 세계에 남긴 반대 선택의 흔적이다.

필드 예시:

- `id`
- `sourceDilemmaId`
- `targetLocationId`
- `axis`
- `rivalChoiceId`
- `summary`
- `evidenceText`
- `worldDelta`
- `relatedNpcIds`
- `canBeIntegrated`

### `WorldState`

현재 세계의 상태를 저장한다.

필드 예시:

- `metrics`
- `resolvedDilemmaIds`
- `rivalMoveIds`
- `locationStates`
- `endingFlags`

### 향후 확장 모델

다음 모델은 장기 비전용이다. MVP에서는 설계만 얇게 남기고 구현하지 않아도 된다.

- `ProfessionProfile`: 직업 노드, 숙련도, 사회적 역할
- `RelationshipState`: NPC별 신뢰, 두려움, 존경, 원한, 기억 요약
- `DilemmaSeed`: AI 생성용 사건 입력값
- `GeneratedDilemma`: AI가 만든 사건, 선택지, 결과, 검증 상태

## 8. 개발 순서

### 1단계: 현재 웹 프로토타입 정리

- 현재 핵심 루프가 깨지지 않도록 테스트를 유지한다.
- 기존 3개 딜레마의 표현을 다듬는다.
- 대칭자의 흔적이 더 잘 보이도록 UI와 텍스트를 정리한다.

### 2단계: MVP 콘텐츠 확장

- 딜레마를 3개에서 5개로 늘린다.
- NPC 3~5명을 정의한다.
- 각 NPC가 플레이어 선택과 대칭자 흔적에 반응하도록 최소 반응 텍스트를 작성한다.

### 3단계: 모바일 UX 검증

- 한 손 조작을 기준으로 화면 흐름을 정리한다.
- 텍스트는 상황 설명 2~3문장, 선택지 2개, 결과 요약 중심으로 줄인다.
- 글자 크기, 터치 타깃, 고대비, 색상 외 표시를 확인한다.

### 4단계: Unity 전환 데이터 계약 확정

- `IdentityProfile`, `Dilemma`, `RivalMove`, `WorldState`를 JSON 또는 C# 모델로 표현할 수 있게 정리한다.
- 웹과 Unity가 같은 도메인 구조를 공유할 수 있는지 확인한다.
- Unity에서 먼저 구현할 기능과 나중에 구현할 기능을 분리한다.

### 5단계: Unity 버티컬 슬라이스

- 작은 지역 1개를 Unity에서 재현한다.
- 이동은 최소화하고, 선택/결과/대칭자 흔적 확인에 집중한다.
- 실시간 전투는 넣지 않거나 더미 처리한다.
- Unity 전환의 목적은 그래픽 확장이 아니라 핵심 루프가 모바일 환경에서도 살아있는지 확인하는 것이다.

## 9. Unity 전환 계획

### 웹 프로토타입에서 가져갈 것

- 정체성 선택 구조
- 대칭자 반전 규칙
- 딜레마 데이터
- 세계 지표
- 대칭자 흔적 생성 규칙
- 통합 엔딩 구조
- 핵심 도메인 테스트

### Unity에서 새로 만들 것

- 모바일 입력
- 씬 전환
- 저장/로드
- 터치 UI
- 간단한 캐릭터 이동
- 장소별 상호작용
- 모바일 성능/해상도 대응

### 전투/이동/3D 월드의 최소 기준

Unity 첫 버전은 전투 중심 RPG가 아니다. 이동과 3D 표현은 선택의 맥락을 전달할 만큼만 만든다.

- 지역 1개
- 고정 카메라 또는 단순 카메라
- 이동 가능한 장소 5~7개
- 전투 없음 또는 단일 이벤트 수준
- 인벤토리 없음
- 스킬트리 없음

### Unity 전환 전 필수 검증 조건

다음 조건이 확인되기 전에는 Unity 대형 개발로 넘어가지 않는다.

- 웹 MVP에서 핵심 루프가 끝까지 작동한다.
- 플레이어가 대칭자를 이해한다.
- 딜레마 결과가 기억에 남는다.
- 텍스트 피로도가 통제된다.
- 데이터 모델이 Unity로 옮길 수 있을 만큼 정리되어 있다.

## 10. 장기 비전

장기 비전은 Unity 기반 모바일 철학 오픈월드 RPG다. 다만 오픈월드는 "맵이 넓다"는 뜻이 아니다. 오픈월드는 플레이어의 직업, 관계, 신념, 대칭자의 흔적이 여러 장소에서 계속 충돌하는 구조다.

### 철학적 오픈월드 RPG

세계는 최종 보스를 향해 닫히지 않는다. 플레이어는 세계 안에서 살아가며 반복적으로 선택하고, 그 결과와 다시 마주한다.

### 직업 네트워크

장기적으로 직업은 전투 클래스보다 넓은 의미를 가진다.

- 치료사
- 상인
- 학자
- 외교관
- 장인
- 교사
- 사제
- 예술가
- 전사
- 탐험가

직업은 플레이어가 어떤 책임을 맡고, 어떤 딜레마를 자주 마주하는지를 정한다.

### 관계 시뮬레이션

NPC 관계는 단순 호감도가 아니라 여러 감정값으로 확장할 수 있다.

- 신뢰
- 두려움
- 존경
- 원한
- 의존

단, 이 시스템은 MVP에 넣지 않는다. 먼저 NPC가 선택을 기억하고 간단히 반응하는 수준부터 검증한다.

### 온라인 AI 서사 생성

장기적으로 AI는 반복 사건, 일상 딜레마, 직업별 의뢰, NPC 갈등을 생성할 수 있다. 그러나 AI는 작가와 시스템을 대체하는 도구가 아니라, 이미 정의된 세계 규칙 안에서 변주를 만드는 도구여야 한다.

### 장기 대칭자 시스템

대칭자는 교체되는 보스가 아니라 플레이어와 함께 성장하는 장기 라이벌이다. 대칭자는 플레이어의 선택을 반박하고, 보완하고, 때로는 플레이어보다 더 설득력 있는 결과를 만든다.

## 11. AI 서사 생성 원칙

### MVP에서는 제외

MVP에서는 온라인 AI 서사 생성을 핵심 기능으로 넣지 않는다. 수작업 딜레마와 규칙 기반 대칭자 반응으로 먼저 게임의 재미를 검증한다.

### 장기 도입 조건

AI 생성을 도입하려면 다음 조건이 필요하다.

- 딜레마 구조가 데이터 모델로 안정되어 있다.
- 좋은 수작업 딜레마의 기준이 확립되어 있다.
- 반복되는 패턴과 금지 패턴이 문서화되어 있다.
- 생성 결과를 검증할 수 있는 서버 로직이 있다.
- 유저당 비용 상한이 계산되어 있다.

### 서버 요구사항

AI 생성을 클라이언트에서 직접 호출하지 않는다. 서버는 다음을 담당한다.

- 프롬프트 조립
- 세계 상태 요약
- 장기 기억 요약
- 생성 결과 검증
- 안전 필터
- 비용 제한
- 캐싱
- 생성 로그
- 사용자별 쿼터

### 반복성과 설교성을 피하는 기준

AI 딜레마는 "자유냐 안전이냐" 같은 추상 질문만 반복해서는 안 된다. 좋은 생성 딜레마는 특정 직업, 특정 NPC, 특정 장소, 과거 선택의 결과를 포함해야 한다.

나쁜 딜레마:

- 추상적 가치만 묻는다.
- 한쪽 선택이 명백히 정답이다.
- 결과가 수치 변화로만 끝난다.
- 플레이어를 설교한다.

좋은 딜레마:

- 특정 NPC가 손해를 본다.
- 선택하지 않은 가치도 설득력 있게 작동한다.
- 대칭자의 논리가 플레이어 선택의 약점을 드러낸다.
- 결과가 나중에 다시 보인다.

## 12. 모바일 UX 원칙

### 세션 길이

MVP의 한 플레이는 5~15분 안에 끝나는 것을 목표로 한다. 장기 버전에서도 사건 하나는 2~5분 단위로 쪼갠다.

### 텍스트량

모바일 화면에서는 철학적 텍스트를 길게 설명하지 않는다.

권장 구조:

- 상황 설명 2~3문장
- 선택지 2개
- 선택 결과 2~3문장
- 대칭자 반응 1~2문장
- 자세한 기록은 접을 수 있는 로그로 분리

### 터치 UI

- 큰 터치 타깃을 사용한다.
- 선택지는 한 손으로 누르기 쉽게 배치한다.
- 전투 조작보다 명확한 선택과 결과 확인을 우선한다.
- 대칭자의 흔적은 지도나 장소 패널에서 쉽게 확인되어야 한다.

### 접근성

MVP부터 다음을 고려한다.

- 글자 크기 조절
- 고대비 모드
- 색상 외 아이콘/텍스트 표시
- 모션 감소
- 자동 저장
- 즉시 재개
- 한 손 조작

### 웹과 Unity 모바일의 차이

웹 프로토타입은 도메인 루프를 빠르게 검증하기 위한 도구다. Unity 모바일 버전은 같은 루프를 모바일 입력, 저장, 성능, 해상도, 배터리 조건 안에서 다시 검증해야 한다.

웹 UI를 그대로 이식하지 않는다. 가져갈 것은 화면이 아니라 루프와 데이터 구조다.

## 13. 수익화 및 운영 원칙

### MVP 단계

MVP 단계에서는 수익화보다 비용과 플레이 패턴 계측이 우선이다.

AI를 실험한다면 다음을 측정한다.

- 세션당 AI 호출 수
- 평균 토큰 사용량
- 생성 실패율
- 필터 차단율
- 유저당 월 비용
- 무료 한도 내 만족도

### 추천 수익화 구조

장기적으로 가장 적합한 구조는 다음 조합이다.

`프리미엄 기본 구매 + 대형 DLC + 선택형 AI 패스/크레딧`

기본 게임은 수작업 캠페인과 대칭자 핵심 루프를 한 번 구매로 완결 제공한다. AI 기반 무한 생활 확장은 선택 기능으로 분리한다.

### DLC

DLC는 이 게임과 잘 맞는다.

- 새 지역
- 새 직업군
- 새 철학 축
- 새 대칭자 서사
- 작가 설계 딜레마 팩

### 코스메틱

코스메틱은 보조 수익원으로만 사용한다.

- 의상
- 거처
- 장비 외형
- 초상화 스타일

단, 철학적 선택 결과나 관계 반응을 코스메틱 과금에 종속시키지 않는다.

### 피해야 할 과금 방식

- 가챠
- FOMO 이벤트
- 능력치 과금
- 선택지 잠금
- 더 좋은 결말 판매
- 더 윤리적인 결과 판매
- 딜레마 진행을 압박하는 토큰 과금

이 게임은 선택과 책임을 다루므로, 과금이 도덕적 판단을 오염시키면 안 된다.

## 14. 다음 2주 작업 계획

### 1~2일차: 기준 문서 확정

- 이 문서를 기준 문서로 삼을지 결정한다.
- MVP와 장기 비전을 명확히 분리한다.
- 기존 4개 문서는 참고 문서로 남긴다.

### 3~4일차: MVP 비목표 선언

- 이번 MVP에서 만들지 않을 기능을 README 또는 개발 문서에 명시한다.
- 특히 오픈월드, 실시간 전투, 무한 AI, 복잡한 관계망을 후순위로 고정한다.

### 5~6일차: 데이터 스키마 확정

- `IdentityProfile`
- `Dilemma`
- `RivalMove`
- `WorldState`

각 모델의 필드와 저장 형식을 정한다.

### 7~9일차: 딜레마 5개 작성

- 기존 3개 딜레마를 유지하거나 개선한다.
- 새 딜레마 2개를 추가 설계한다.
- 각 딜레마마다 대칭자 반응과 재방문 텍스트를 작성한다.

### 10~11일차: 모바일 와이어프레임 작성

- 정체성 선택 화면
- 지도/장소 화면
- 딜레마 선택 화면
- 결과 화면
- 대칭자 흔적 화면
- 통합 엔딩 화면

### 12~14일차: 소규모 플레이테스트

3~5명에게 플레이시킨 뒤 다음을 기록한다.

- 대칭자 이해도
- 선택 몰입도
- 기억에 남은 결과
- 텍스트 피로도
- 다시 플레이 의향
- 헷갈린 UI 지점

이 피드백을 바탕으로 Unity 전환이 아니라 웹 MVP의 핵심 루프를 먼저 다듬는다.
